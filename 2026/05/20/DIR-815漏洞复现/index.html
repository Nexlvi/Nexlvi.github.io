漏洞编号：CNVD-2013-11625
目标固件：DIR815A1_FW103b01.bin（D-Link DIR-815 Rev.A 1.03b01）
架构：MIPS32 Little Endian
复现方式：QEMU user-mode 本地仿真，无需真实路由器

第二步：找到漏洞所在的文件

2.1 从 HTTP 入口开始找

路由器的 Web 界面通过 CGI 程序处理请求。先看 Web 目录：

你会发现：
![[Pasted image 20260521021717.png]]

所有 .cgi 文件都是软链接，全部指向同一个真实二进制 /htdocs/cgibin。

这个 cgibin 根据被调用时的文件名（argv[0]）来决定执行哪个功能——类似 BusyBox 的做法。

2.2 确认 cgibin 的架构以及保护

![[Pasted image 20260521021953.png]]

关键信息：

  • MIPS 32-bit Little Endian（LSB = Least Significant Byte first）
  • 动态链接，依赖 uClibc（嵌入式 Linux 精简版 libc）
  • stripped（符号表被删除，没有函数名）

安全保护情况：

保护 状态
NX（栈不可执行） ❌ 无
Stack Canary ❌ 无
PIE（地址随机化） ❌ 无
RELRO ❌ 无

没有任何保护 → 直接往栈上写 shellcode 然后跳过去执行，最简单的利用方式。

首先这是本来就揭露的漏洞，本文章也主要是教学学习为主，所以我们已知漏洞点函数为hedwigcgi_main

![[Pasted image 20260521023753.png]]

sprintf(buf, "%s", uid) 把用户可控的 uid 无限制地写进 1024 字节的栈缓冲区 → 经典栈溢出。

第三步：GDB 调试，精确定位偏移

知道能溢出还不够，要精确知道 payload 的第几个字节覆盖了 $ra。

3.1 用 De Bruijn 序列定位 $ra 偏移

发 1100 个 A 只能证明溢出存在。De Bruijn 序列（pwntools 的 cyclic）任意连续 4 字节全局唯一，崩溃时看 $pc 就能反查偏移。

c 之后程序带着 1100 字节的 cyclic 序列跑起来，直接崩溃：

![[Pasted image 20260807203543.png]]

0x61616c6b 就是 cyclic 序列里被写进 $ra 的那 4 个字节——是个无效地址，CPU 跳过去就崩了。

⚠️ 崩溃值因 QEMU 版本而异：本文环境（QEMU 11.0.2）实测是 0x61616c6b；早期 QEMU 8.x 实测是 0x6b61616c。以你自己 GDB 看到的实际值为准，方法不变，两种值算出来的偏移都是 1043。

看寄存器，确认是 jr $ra 导致的跳转：

![[Pasted image 20260807205853.png]]

为什么 to_bytes(4, 'little')？MIPS 小端下 0x61616c6b 在内存里实际是 6b 6c 61 61（低字节在前），cyclic_find 搜索的是原始字节序列，必须转成小端字节再搜。

$ra 偏移 = 1043 📌 —— 意思是 payload 的第 1043 字节开始的那 4 字节，会覆盖 $ra。

3.2 偏移 1032 的陷阱：SIGBUS

调试中发现一个坑：payload 不够长时崩溃的是 SIGBUS 而不是 SIGSEGV。

原因： hedwigcgi_main 的尾声除了恢复 $ra，还会恢复若干 $s0~$s7，其中偏移 1032 处的寄存器在函数返回前会被当成指针解引用。如果那里是 0x41414141（无效地址），程序还没走到 jr $ra 就先崩了。

解决： 偏移 1032 处放一个合法栈地址（如 0x2b2aad30，在栈范围内），让解引用顺利通过，走到 jr $ra。

第四步：确认内存布局，找 shellcode 落点

4.1 各段加载在哪

![[Pasted image 20260807203841.png]]

⚠️ 这些地址会随 QEMU 版本漂移！ 上表是 QEMU 11.0.2 实测值。笔者 5 月第一次复现时 QEMU 还是 8.x，当时栈在 0x2aaac000~0x2baac000、shellcode 落点 0x2baab880；后面换到 QEMU 11.0.2 后栈基址整体下移了 1MB，旧地址全部失效。换环境/换版本必须重新实测——好在方法不变：GDB 探针测 $sp、info proc mappings 看栈范围。

QEMU user-mode 默认关 ASLR，所以每次运行布局完全一致，shellcode 地址可以写死。

4.2 探针 payload 实测 shellcode 落点

shellcode 紧跟在 $ra 后面放。函数 jr $ra 时延迟槽 addiu $sp, $sp, 0x450 执行完，$sp 正好指向 $ra 之后的数据 → shellcode 地址 = 崩溃时的 $sp。

发一个探针 payload（$ra 填 BBBB，shellcode 位置放 E 占位）：

GDB 里崩溃后：

![[Pasted image 20260807204705.png]]

SHELLCODE_ADDR = 0x2b2ab880 📌

⚠️ 这个地址和 payload 大小强相关：QEMU 把所有环境变量压到栈顶，cookie 越大初始 $sp 越低。必须用与最终 exploit 完全相同大小的 payload 来测 $sp，否则地址漂移。
⚠️ 环境变量要最小化（只用上面 6 个），不能用 os.environb.copy() 继承父进程全部变量，否则不同终端下 $sp 不一致。

第五步：编写 MIPS LE shellcode

目标是 execve("/bin//sh", ["/bin//sh", NULL], NULL) 的机器码，且不含 null 字节（sess_get_uid 用 C 字符串处理 cookie，遇 \x00 就截断）。

三个坑：

  1. MIPS 小端字符串陷阱：sw 是低字节先写低地址，寄存器里要放翻转后的字节序。如 /bin = 0x2f62696e，寄存器要装 0x6e69622f，sw 后内存才是 2f 62 69 6e。
  2. 构造 0 不能直接 move：move/xor 的机器码含 \x00。用 slti $t6, $zero, -1（有符号比较 0 < -1 为假 → 结果为 0），机器码 0x280effff 无 null 字节。
  3. argv 数组不能和字符串重叠：argv[1] 会读到字符串字节当成指针 → execve 返回 EFAULT。字符串放 $sp-24，argv 数组放 $sp-12。

![[Pasted image 20260807205224.png]]

常见报错与排查

报错 原因 解决
SIGBUS 偏移 1032 处是无效地址，尾声解引用指针先崩 1032 处填合法栈地址（0x2b2aad30）
SIGILL 跳到了 shellcode 地址但内容不对（地址偏了） x/10i 0x2b2ab880 看是不是自己的指令；用完整 payload 重测 $sp
-E HTTP_COOKIE=...: invalid option / cookie 被截断 QEMU -E 按逗号分隔，shellcode 含 0x2c 改用 Python env= 字典传环境变量
$sp 每次运行不一样 用了 os.environb.copy()，环境变量数量/大小不定 只用 6 个最小化环境变量
execve 后无输出（exit=0） shell 起来了但命令没发进去 换交互式版本手动输入验证

总结

完整攻击链：

这个洞能成立，本质是三层叠加：

  1. 代码层：sprintf 无长度限制，C 语言经典错误（应换 snprintf）；
  2. 编译层：无 canary、无 NX，栈上直接执行，2013 年嵌入式固件的常态；
  3. 运行层：QEMU user-mode 关 ASLR + 无 PIE，地址可预测，利用难度大幅下降。
